Diffing Protocol Buffers schemas

Because a .proto file defines a wire contract, changes to it have compatibility consequences — some safe, some breaking. Diffing two schema versions before you regenerate and ship is how you catch the breaking one.

What to watch in a .proto diff

  • Field numbers are the contract: reusing or changing a number breaks compatibility with existing serialized data. A changed number is the highest-signal thing here.
  • Removed or renamed fields — renaming is safe on the wire (numbers matter, not names) but removing and reusing a number is not.
  • Type changes and required/optional/repeated edits.
  • Reserved ranges added to protect retired field numbers.

Your schema stays in your browser — nothing is uploaded, which suits internal service contracts.

Field numbers are the contract, not the names

The single most important rule when reviewing a .proto diff: field numbers are what serialisation depends on, not field names. Renaming a field is safe on the wire and breaks only generated code. Changing a field's number, or reusing a number that a removed field previously held, breaks every client that hasn't been redeployed — silently, by decoding bytes into the wrong field rather than by erroring.

So when reading a protobuf diff, check the numbers first and the names second, which is the opposite of how the eye naturally scans. A removed field should leave behind a reserved entry for its number and name; a diff that removes a field without adding one is the change most likely to cause a problem months later when someone reuses the slot.

Type changes are the other high-risk edit. Some are wire-compatible (int32 to int64), some are quietly not (int32 to string), and the diff looks identical in both cases — one word. Check the compatibility table rather than assuming.

Common questions

Can this tell me if a schema change breaks wire compatibility?

It shows you exactly which lines changed — a reused or renumbered field tag, a field removed instead of marked reserved, a changed type on an existing tag — but it's a text diff, not a protobuf compiler, so judging whether a specific change is breaking is still yours to make from what it highlights.

What should I look for in the diff to catch a breaking change?

Field tag numbers (the `= 1`, `= 2` at the end of each field) that were reused or renumbered, a field deleted without being added to `reserved`, and a field's type changed to one that isn't wire-compatible with the old type — all show up as ordinary changed lines.

Does it work for proto2 and proto3?

Yes — both are plain text, so a `.proto` file compares the same way regardless of syntax version.

Is my schema uploaded anywhere?

No. The comparison runs entirely in your browser, so an unreleased API schema never leaves your device.
