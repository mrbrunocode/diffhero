Diffing Gleam code

Gleam is statically typed and runs on the BEAM, and its diffs turn on the same things any strongly-typed functional language does: the shapes of types and the branches of pattern matches. A small type change ripples, so it's worth diffing types closely.

What to look for

  • Custom type and constructor changes that alter the shape of your data.
  • case expression arms — a changed or reordered pattern.
  • Pipe (|>) sequences and use expressions.

Gleam has a built-in formatter, so gleam format both sides for the cleanest result. All comparison is client-side — nothing is uploaded.

What to look for in a Gleam diff

Gleam's type system means many changes that would be runtime bugs elsewhere are compile errors here — which shifts what's worth scrutinising in a diff. Pattern matches are the high-value target: a removed case arm may still compile if the match was already inexhaustive somewhere upstream, and an added variant to a custom type ripples out to every case that handles it.

Watch the pipelines. Gleam code leans heavily on |> chains, and inserting or removing a stage mid-chain shifts everything downstream by one position. Word-level highlighting helps here: the line looks broadly similar, and the meaningful change is a single function name in the middle of it.

Because Gleam compiles to both Erlang and JavaScript, also note changes to external function bindings — an @external annotation pointing at a different target module is a substantial change dressed up as one short line.

Common questions

Does it understand Gleam's type system?

No — it's a text diff, so it doesn't check types. It still shows exactly which type signature or case-match arm changed, which is what a code review actually needs.

Does it work for gleam.toml too?

Yes, any plain-text file works — paste the manifest to see dependency or version changes the same way.

Is my Gleam source uploaded?

No. Everything runs in your browser, so unreleased source stays private.
